# 门区报修工单与备件系统 —— 设计说明

替换纸质流程的一套车间域服务：门区报修开单、备件预占/实扣、修完关单解锁、
超期分级提醒负责人。代码在 `psdline/workshop/`，纯标准库，沿用仓库已有的
`JsonStore`（原子快照）+ `JsonlJournal`（只追加流水）设施。

- 端到端演示：`PYTHONPATH=. python3 -m psdline.workshop.demo`
- 测试：`tests/test_workshop_*.py`（4 个文件，38 个用例）

## 1. 状态机

    OPEN ──repair──▶ REPAIRED ──close──▶ CLOSED
      │                  │
      └────────void──────┴────────void────▶ VOIDED

- 开单即**锁定门区**（同一门区同时只允许一张活动工单，重复开单被拒）；
  锁事件 `DOOR_LOCKED` 与开单在**同一事务**落盘；
- 技师 `mark_repaired` 报完工后仍可补领料（验收时缺件是常态）；
- **只有主管** `close_order` 关单，同事务落 `DOOR_UNLOCKED`；
- 主管 `void_order` 废单同样解锁；CLOSED / VOIDED 之后历史冻结，再做任何
  动作抛 `OrderClosed`。

## 2. 备件：开单预占 + 领料实扣（两阶段）

两种方案都可行，这里选**预占**，原因是现场最痛的是"单开了、件早被别的单
拿走了"。

| 时点 | on_hand（在架实物） | reserved（预占） | available |
|---|---|---|---|
| 开单预占 4 | 不变 | +4 | 减 4 |
| 领料实发 3 | -3 | -3 | +1（释放占用） |
| 关单，未领 1 | 不变 | -1 | +1（自动回补） |

- 跨班：白班开单、夜班仓管发料，领料不校验班次/开单人，只校验角色与数量，
  每次发料都记在**同一张工单**的不可变历史里；
- 一个领料批是**原子**的：批内任意一件超预占余量或在架不足，整批回滚
  （深拷贝试投影，失败不碰内存状态、不写流水），不会出现"电机出了、密封圈
  没出"的半成品账；
- 库存恒等式每次提交后校验：
  `on_hand = registered_total - issued_total + returned_total + adjust_total`，
  且 `0 <= reserved <= on_hand`。

**为什么不是"修完再实扣"**：那种模式开单不占件，两张单都写"需要仅存的 1 台
电机"，先修的拿走、后修的停工等件，且纸质流程最核心的"对不上"无法在开单时
暴露。预占把缺货冲突提前到开单一刻，代价是主管要定期清理长期不领料的僵尸
单（废单即释放），这个代价值得。

## 3. 废单与库存回补：自动 + 人工确认 分开处理

- **未领的预占量：系统自动回补**（`ORDER_VOIDED.released` 同事务落账）。
  件还在货架上，没人接触过，没有理由要人确认；
- **已经领走的件：必须人工确认流向**——仓管 `return_parts` 实物退库（在架
  回补），或主管 `write_off_parts` 核销（必须填原因，库存**不**回补）。
  已领未清不为零时废单直接被拒。

原因：件一旦出了库房门，可能已经装到别的门上、丢了、拆封了，系统无法替人
断定它在哪；自动回补会凭空造出不存在的库存，比纸质流程更糟。

| 开单 / 派活 | ✓ | | ✓ | ✓ |
| 发料、退料签收 | | ✓ | ✓ | |
| 报修完工 | ✓ | | ✓ | |
| **关单 / 废单** | | | **✓（唯一）** | |
| 备件核销 | | | ✓（必须填原因） |
| 盘点上报差异 | | ✓ 可上报 | ✓ | |
| **盘亏盘盈调账** | | | **✓（唯一批准）** |

关单权单独收到主管：谁修谁关会让"修完才解锁"失去独立验收这一层，门没修好
就解锁是安全事故。

## 5. 一致性机制（事件溯源）

所有状态都是只追加事件流（`workshop-*.jsonl`，fsync 落盘）的投影：

- **提交协议**（`WorkshopRegistry.commit`）：取全局锁 → 在提交前状态上跑
  权限/前置校验 → 锁内构造事件（关单释放量按最新台账算）→ 深拷贝试投影 +
  恒等式校验 → 分配递增 seq 顺序追加流水 → 原子替换快照（临时文件 +
  `os.replace`）。任一步失败：内存与流水都不留痕迹；
- **并发**：唯一串行化点是注册表层的锁，8 线程抢 10 件库存的用例中恰好
  5 笔成功、无超发、流水重算与在线账一致（`test_workshop_concurrency.py`）；
- **工单历史不可变**：事件只追加、无 UPDATE/DELETE 型事件；seq 全车间严格
  递增；终结后的工单拒绝一切写操作；
- **崩溃恢复**：
  - 快照在 → 快照 + 流水尾部补齐；
  - 快照缺失/损坏/不平 → 从第 1 条事件全量重放，落 `SNAPSHOT_REBUILT`
    审计事件（"库存对不上时的恢复"有痕迹可查）；
  - 流水末尾半行（提交中途掉电）→ 只允许截断**最后一段末尾**的坏行，中间
    坏行拒绝启动，绝不静默吞掉；
- **对账**：`verify_stock()` 比对在线台账与流水全量重算；主管
  `recover_stock()` 以流水为唯一真相重建（流水本身重放不平则直接报错，
  不可自动"修平"）。

## 6. 超期提醒

`scan_overdue()`（建议挂定时器，换班时也扫一次）对活动工单分级，同一级别
只发一次（去重状态也由事件投影，重启不丢）：

- L1：过 `due_at` 即提醒**负责人本人**；
- L2：超期 4 小时（默认，可配）加抄**调度**，对应跨班无人接手；
- L3：超期 24 小时升级**主管**。

终结工单不再提醒。通知出口是可注入的 `notifier` 回调（演示里打印
`[外部通知]`，现场可接短信/对讲机/企业 IM）。

## 7. 文件结构

| 文件 | 职责 |
|---|---|
| `workshop/events.py` | 13 种不可变事件、类型白名单 |
| `workshop/models.py` | 人员/备件/工单行/工单只读视图 |
| `workshop/inventory.py` | 库存投影、预占/领料校验、台账恒等式与重算 |
| `workshop/orders.py` | 工单状态机投影、门区活动索引、履约数量 |
| `workshop/lockout.py` | 门区锁派生视图与锁动作历史回放 |
| `workshop/registry.py` | 事务提交、快照、回放、半行恢复、对账重建 |
| `workshop/reminders.py` | L1/L2/L3 分级、升级与去重 |
| `workshop/service.py` | 门面：权限矩阵 + 全部用例编排 |
| `workshop/demo.py` | 跨班、并发、超期、废单、盘点、恢复的全流程演示 |

## 8. 已知边界（当前取舍）

- 单进程多线程并发（与仓库其余模块一致）；多实例部署需要把流水目录放到
  支持原子 rename 的共享卷，并以文件锁或单写者方式串行化提交；
- 提醒依赖外部定时调用扫描器；
- 人员/备件主数据的变更（离职、件码停用）本期未做，现场可由主管新建件码
  替代；旧件码在历史事件中保持原样不动，保证回放不被污染。
